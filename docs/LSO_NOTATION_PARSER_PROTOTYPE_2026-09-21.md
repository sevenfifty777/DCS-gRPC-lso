# The DCS LSO comment read against the NATOPS glossary: prototype and before-and-after on 160 recorded comments

Branch `jev-plan`, 21 September 2026. Follow-up to `docs/TYPESAFE_JUDGMENT_OPPORTUNITIES_2026-09-21.md`, opportunity 1, done **without any AI**: a deterministic parser built from the shorthand glossary in `docs/NATOPS/LSO-NATOPS-MAY09.pdf` (NAVAIR 00-80T-104, sections 11.4.1 to 11.4.3), run over every distinct DCS comment in the recorded corpus next to what `src/lso_notation.rs` produced before this document. This document shows what the live "LSO Notes" line in Discord and on the greenie board becomes, and what the parser yields beyond that line.

**Implemented on this branch the same day** (later commits than this document's first version): `src/lso_notation.rs` is now this parser (`parse`, `Notation`, `to_english`), the `WIRE#` reader, the waveoff-initiator reader and the `grade-ab` label read the same parse, the 160 comments are the module's test corpus (`tests/fixtures/dcs_lso_comments.txt`), and the reverse renderer `from_episodes` writes the project's own graded episodes in the same shorthand when DCS wrote nothing (Discord fields "LSO Notation (measured by LSO, not a DCS comment)" and "LSO Notes (measured by LSO, not a DCS comment)"). The "today" column in appendix A is therefore the output of the previous translator, kept as the record of what changed. The report field `dcs_grading_parsed` and the `grade-ab` DCS-versus-project comparison (section 2.4, step 4) are not implemented yet.

## 1. In plain language

**What was run.** The 160 distinct comments DCS wrote on the 165 recorded passes that carry one (JSON reports under `tools/aoa_calibration/` and `trap_records/`, plus the `dcs.log` files). For each, the current translator's output and the prototype's output, side by side (appendix A), and the typed rows the prototype extracts (appendix B).

**Result.** The prototype reads all 160 without a single unknown token and without a single ambiguous one. Every comment in the corpus is built from 20 glossary symbols plus the waveoff symbol, 6 suffixes, 3 modifiers, 8 grade labels and the `WIRE# n` / `[BC]` markers. The current translator, which was written from invented examples, gets the magnitude backwards, loses the position on every underlined token, mistranslates the five most frequent tokens, and prefixes every waveoff with six spurious deviations (the reasons are in the TypeSafe document, Part 1).

**What a pilot would see change**, on a real comment:

|---|---|
| DCS writes | `LSO: GRADE:C : _SLOX_  _TMRDAR_  _DRX_  (LURIM)  _DRIM_  WIRE# 2 _EGIW_ [BC]` |
| Discord today | Slightly slow, slightly turning, slightly drift, slightly drift, a little lined up right, a little lineup, slightly drift, slightly lineup |
| Discord after | Slow at the start (gross), too much rate of descent at the ramp (gross), drifted right at the start (gross), a little lined up right in the middle, drifted right in the middle (gross), eased gun in the wires (gross); wire 2; ball call |

And on a waveoff:

| | |
|---|---|
| DCS writes | `LSO: GRADE:WO  _DRX_  _LURX_  _SLOX_  LOIM  _LOIC_  WOFDIC [BC]` |
| Discord today | Low, slow, glide slope, drift, energy (AoA), wings not level, slightly drift, slightly lined up right, slightly slow, low in the middle, slightly low, slightly lineup, wings not level, fast, drift, lineup |

**What the pilot sees in the cockpit, per size.** Parentheses are "a little": a deviation the LSO noticed but would not call. Plain is a moderate deviation, the one the LSO would have called ("power", "right for lineup"). Underlined (DCS writes it with underscores) is the NATOPS emphasis, which the project's grading convention (`docs/GRADING_CONVENTION_PROTOTYPE_2026-09-15.md`) reads as the gross deviation: the one that by itself makes the pass a `--` unless corrected early. The rendered line marks it "(gross)" so the reader sees which deviations decided the DCS grade.

**What the parser gives beyond the sentence.** Each token becomes a row `symbol @ position / axis / size`, for example `TMRD@AR/glideslope/gross`. That is the shape of the grader's own episodes (`axis`, `Small`/`Medium`/`Large`, `Start`/`Middle`/`InClose`/`Ramp`), so `grade-ab` can print, per pass and per axis, whether DCS's LSO and the project saw the same deviation in the same third of the groove. Appendix B has those rows for all 160 comments. The grade label and the wire come out of the same parse, which retires the three other copies of that logic (`src/track.rs` `parse_dcs_wire`, `src/grading.rs` `dcs_waveoff_initiator`, `src/commands/grade_ab.rs`, and `tools/aoa_calibration/align_aoa.py`).

**What this changes live.** Only the "LSO Notation" / "LSO Notes" fields of the Discord embed and the `lso_notes` column of the greenie board (`src/db.rs`), which is computed from the stored comment at read time, so historical rows are corrected the moment the parser is. No grade, wire estimate or outcome depends on this parser today, and none would after the change: the DCS wire still comes from the same `WIRE#` digits, the DCS waveoff initiator from the same label.

**Three readings** the prototype had to choose, settled the same day (`docs/LSO_SHORTHAND_GLOSSARY.md`, section 7):

1. `[BC]` means the ball call was made. DCS can only record it when the pilot's communications with the ship are working, so its absence means "not confirmed", not "not answered" as the NATOPS square would suggest.
2. `W` is rendered "wings not level" (glossary: "Wings"), which is what the DCS LSO means by `WX`. The tables in this document's appendices predate that change and show "wings".
3. Parentheses directly after `WO` (`WO(AFU)IC`) hold the waveoff's reason, not "a little".

## 2. Technical

### 2.1 The grammar the corpus follows

```
comment  := "LSO:" ws "GRADE:" ws? label ( ws ":" ws body | ws body )
label    := "_OK_" | "OK" | "(OK)" | "---" | "C" | "WO" | "OWO" | "NC"        (seen)
          | "--" | "WOP" | "B"                                             (NATOPS, not seen)
body     := token ( ws token )* | free text after "NC"
token    := "WIRE#" ws? digit suffix?                                      wire, e.g. "WIRE# 3[BC]"
          | "[BC]"                                                          ball call
          | "WO" ( "(" symbols ")" | symbols ) suffix?                      waveoff with reason
          | "(" symbols ")" suffix?                                         a little
          | "_" symbols suffix? "_"?                                        emphasis (gross)
          | symbols suffix?                                                 moderate
symbols  := one or more glossary symbols, longest match first
suffix   := X | IM | IC | AR | TL | IW | AW | BC | OT | CCA
```

Waveoff comments use two spaces after the label instead of ` : `, on all 38 of them. One comment carries a broken token `_PP _PIC_` (a single space inside), which the parser reads as two tokens, "power (two calls)" and "power in close"; the intended reading is probably "power, power, power in close" but the string does not say so.

### 2.2 Symbols actually used by DCS (out of about seventy in the glossary)

| Symbol | Meaning | Axis | Symbol | Meaning | Axis |
|---|---|---|---|---|---|
| `SLO` | slow | speed | `DR` / `DL` | drifted right / left | lineup |
| `F` | fast | speed | `LUL` / `LUR` | lined up left / right | lineup |
| `LO` | low | glideslope | `LL` / `LR` | landed left / right | landing |
| `H` | high | glideslope | `3PTS` | landed three points | landing |
| `TMRD` | too much rate of descent | glideslope | `LNF` | landed nose first | landing |
| `P` | power (repeated: `PP`, `PPP`) | power | `NSU` | not set up | pattern |
| `EG` | eased gun | power | `AFU` | all fouled up | other |
| `N` | nose | attitude | `FD` | fouled deck | deck |
| `W` | wings | attitude | `WO` | waveoff (with reason) | outcome |

Suffixes seen: `X` (start), `IM` (middle), `IC` (in close), `AR` (ramp), `TL` (to land), `IW` (in the wires). Not seen: `AW`, `OT`, `CCA`.

### 2.3 Segmentation and why no AI is needed

For each token the parser strips the modifier, tries every suffix the token ends with, and enumerates every way to cut the remainder into glossary symbols. It prefers a reading with a suffix, then the reading with the fewest symbols (longest matches). On this corpus every token has exactly one best reading; the only token with two full segmentations at all is `SLOX` (`SLO`+`X` or `S`+`LO`+`X`, "settling low at the start"), and the fewest-symbols rule picks the right one. If a future comment produced a genuine tie or an unknown symbol, the parser reports it in the output line ("not understood: …") rather than dropping it, and a `warn!` would carry it to the log. That is the point where a judgment model could be asked to pick between readings; nothing in 160 comments needed it.

### 2.4 Landing it in the code

1. Replace the body of `src/lso_notation.rs` with the glossary parser: `parse(&str) -> Parsed` (grade, wire, deviations as typed rows, ball call, unknown tokens) and `to_english(&Parsed) -> String`. Keep the public `to_english(&str)` signature as a thin wrapper so `src/db.rs:344` and `src/tasks/record_recovery.rs:2041` do not change.
2. Point `parse_dcs_wire` (`src/track.rs:5199`), `dcs_waveoff_initiator` (`src/grading.rs:571`) and the label extraction in `src/commands/grade_ab.rs:495` at `Parsed.wire` and `Parsed.grade`. Behaviour is identical on the corpus; `WOP` becomes a pattern waveoff instead of an LSO one.
3. Replace the nine invented test strings with the 160 recorded comments and the expected rows (appendix B is the answer key, once the three open readings are settled).
4. Serialise `Parsed` into the schema-v3 report as `dcs_grading_parsed` so `grade-ab` can compare DCS rows with the grader's episodes per axis and zone. This is the one addition with reach beyond the notes line; it is a code feature, not an AI one.
5. Leave `tools/aoa_calibration/align_aoa.py:424` reading the label from the report field once step 4 exists.

Rendering choices to settle when porting: whether to keep the "(gross)" marker or the word "very"; whether to group by size or keep DCS's order (the prototype keeps the order, which follows the pass from the start to the wires).
